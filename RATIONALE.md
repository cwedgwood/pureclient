# Rationale

Why this client exists in its current shape. This is the
maintenance-essentials version; before/after detail belongs in
[MIGRATION.md](MIGRATION.md).

## What changed and why

This client targets **FlashArray REST API v2.26**, generated by
**[oapi-codegen](https://github.com/oapi-codegen/oapi-codegen) v2.7.0**.
The previous incarnation targeted **v2.8** generated by
**swagger-codegen-go** - both significantly out of date.

- v2.26 is the highest v2 API exposed by Purity 6.5.x and stays
  inside the Swagger 2.0 spec format (the cutover to OAS 3 happened
  at v2.42). Bumping further is a small patch when needed;
  `generate.sh` already detects the format change.
- oapi-codegen is a Go-native generator (`go install`, no Java/JVM
  for the day-to-day path) producing idiomatic output: pointers for
  optional fields, per-operation methods on a flat client, request
  editors instead of context-key auth, typed response structs.
  swagger-codegen's Go template is a Java port and its development
  is effectively dormant.
- The upstream FA2.26 spec is still Swagger 2.0, which oapi-codegen
  doesn't parse. The conversion to OAS 3 is a one-shot step using
  openapi-generator via Docker; the resulting spec is committed at
  `client/api/openapi.yaml` with provenance in its header. Routine
  regen does not need Docker.

The migration is breaking; there is no compatibility shim. See
[MIGRATION.md](MIGRATION.md).

## Trade-offs you will hit

These are documented so they don't have to be rediscovered.

1. **`allOf` collapse to `map[string]interface{}`.** oapi-codegen
   does not synthesize typed structs for `allOf`-composed nested
   objects. The current spec contains 51 such collapses
   (`grep -c '= map\[string\]interface{}' client/types.gen.go`),
   covering things like `Volume.Qos`, `Volume.Space`,
   `Volume.PriorityAdjustment`, `Audit.Origin`, and most
   directory-service nested config. Workaround: construct map
   literals using the field names from `client/api/openapi.yaml`,
   or add `x-go-type` annotations and re-derive (we have not done
   this - it would mean maintaining a parallel set of edits across
   every upstream refresh).

2. **Verbose method names tied to URL structure.**
   `GetApi226ProtectionGroupsSnapshotsTransferWithResponse` is the
   canonical shape. `x-go-name` annotations could shorten them; we
   haven't added them, same reason as above.

3. **Optional fields are pointers everywhere.**
   `if vol.Name != nil && *vol.Name == "foo"` is the cost of
   distinguishing absent from empty, which the API relies on for
   PATCH semantics.

4. **Generated identifiers may shift on regen.** Spec renames ->
   Go-type renames. Pin to a tagged release if stability matters.

## Versioning

Release tags stay in the `v0.x` range on purpose: a `v2`-or-higher
module would require a `/v2` import-path suffix
(`github.com/cwedgwood/pureclient/v2`), which every consumer would
have to adopt. Staying in `v0.x` keeps the import path stable.

The **minor** version encodes the FlashArray API version the client
targets, as `API-major x 100 + API-minor`:

| Tag        | FlashArray API |
|------------|----------------|
| `v0.226.x` | 2.26           |
| `v0.242.x` | 2.42           |
| `v0.246.x` | 2.46           |

The **patch** field is free for client-only fixes on the same API
version (e.g. `v0.226.1` is a fix to the 2.26 client). In `v0.x`,
a minor bump also signals a breaking change - which lines up, since
moving to a new API version is breaking for consumers.

(The `x 100` encoding would collide if an API minor ever reached
100 - `2.100` -> `300` clashes with a hypothetical `3.0`. Not a
concern for the current 2.x line; switch to `x 1000` if it ever
becomes one.)
